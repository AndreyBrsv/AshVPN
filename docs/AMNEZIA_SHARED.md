# Shared AmneziaWG management

**Experimental: shared management may not work with your AmneziaVPN version or VPS.** It is an unreleased local feature intended for v0.0.12. Kernel and server-side traffic checks do not establish official GUI adoption, cross-manager edits or external reachability. Use host mode when you only need Ashapp administration and a client import in AmneziaVPN.

## Two installation choices

- **Shared kernel (default for new setups and templates):** a real `amnezia-awg2` Docker container uses the host's AmneziaWG kernel module, with the compatible configuration and `clientsTable` intended for management from Ashapp and AmneziaVPN. Current live adoption is still being verified. This requires a Linux x86_64 VPS; the computer running Ashapp can still be Windows or either supported macOS architecture.
- **Host kernel:** AmneziaWG runs directly on Linux. Ashapp manages the server and devices. Import a device's `vpn://` key or `.conf` in AmneziaVPN to connect. Its administrator SSH flow does not adopt this host service.

New manual setups and templates select shared kernel mode initially. Choose host mode explicitly when wanted. Existing templates preserve their saved choice; legacy template JSON without `awg_deployment` still loads as host mode. This default change does not migrate existing servers or rewrite saved templates. Setup refuses to replace, adopt or migrate another VPN deployment.

Docker is packaging here, not evidence of userspace processing. The installer loads the reviewed kernel package, removes the Go fallback from its derived image, creates an actual `type amneziawg` interface and checks the active interface, listening port, process list and startup guard. It refuses to report success when those checks are incomplete.

For a **new** shared deployment, Ashapp generates actual AmneziaWG 2 parameters: S3/S4 and non-overlapping H1-H4 ranges. Earlier development code reused the legacy host parameter set inside an `amnezia-awg2` container. AmneziaVPN infers the protocol generation from the configuration, so that combination could be displayed as legacy even though its container name looked modern. Existing installations and their keys are never upgraded in place. Client `vpn://` exports select the matching container and explicit `protocol_version` from the original client parameters, preserving the original identity and native `.conf` export. The inference follows the official [AWG model](https://github.com/amnezia-vpn/amnezia-client/blob/de93650a90739b87bb47a632872ea9d0adc9412f/client/core/models/protocols/awgProtocolConfig.cpp) and [installer](https://github.com/amnezia-vpn/amnezia-client/blob/de93650a90739b87bb47a632872ea9d0adc9412f/client/core/installers/awgInstaller.cpp).

The PPA package indexes inspected on 2026-11-06 for focal and noble contained module commit `4569c4c` and tools commit `ee0f0a9`; that module's [netlink implementation](https://github.com/amnezia-vpn/amneziawg-linux-kernel-module/blob/4569c4c/src/netlink.c) supports those parameters. APT still verifies repository signatures during installation, and kernel activation must accept the generated configuration. This observation is not a pin on mutable package indexes and does not replace testing the actual installed module.

## Using both managers

Create devices in Ashapp, then add administrator SSH access in AmneziaVPN. In version 5.0.3.0, **Choose Installation Type** appears before server discovery. **Automatic → Continue** selects `amnezia-awg2`, scans running containers and reuses the matching installation before deciding whether installation is needed. The installation-looking page alone does not establish that the container was missed. Discovery uses `docker ps`, so the shared container must be running; a stopped container is not discovered. The actual discovery/adoption flow still needs this implementation's completed real-GUI verification. The sequence follows the official [wizard](https://github.com/amnezia-vpn/amnezia-client/blob/de93650a90739b87bb47a632872ea9d0adc9412f/client/ui/qml/Pages2/PageSetupWizardEasy.qml) and [installation controller](https://github.com/amnezia-vpn/amnezia-client/blob/de93650a90739b87bb47a632872ea9d0adc9412f/client/core/controllers/selfhosted/installController.cpp).

Refresh after using the other application. Edit from one manager at a time: AmneziaVPN does not participate in Ashapp's transaction lock. Ashapp checks snapshots and applies selected-peer changes, but that cannot guarantee atomic editing against another application that does not honor the same lock.

External `amnezia-awg` and `amnezia-awg2` containers are **AmneziaWG protocols managed by AmneziaVPN**, not a separate protocol named after the app. Ashapp reports their actual configuration generation, published port and observed kernel/userspace data plane separately from ownership. It does not adopt them as its own installation, silently switch their engine, or apply owned-service reset controls to them. New Ashapp-created client addresses are appended above the existing saved/runtime peers; reusing a lower hole can cause older AmneziaVPN versions, which allocate from the final saved peer, to reuse another device's address.

Each device keeps its own identity and can be revoked independently. A `vpn://` export gives device access; it never carries SSH credentials or the server private key. Existing exports do not regenerate keys. Clients created in AmneziaVPN may not have their original private configuration stored on the server; import their original `.conf` into Ashapp to enable later key/file/QR access. A private key cannot be recovered from its public key.

The common management scope is AmneziaWG clients and the shared service. Ashapp templates, SSH policy, Fail2ban, firewall, update policy and the separate sing-box VLESS service remain Ashapp features. Private SOCKS5 remains an Ashapp SSH tunnel: AmneziaVPN's service discovery can show the same proxy without recognizing its loopback-only publication. Its direct remote SOCKS5 details do not establish that it is publicly reachable. Do not use that other application's proxy reinstallation to manage private exposure.

### SOCKS5 credentials in the other application

Ashapp and AmneziaVPN read the same server file, `/usr/local/3proxy/conf/3proxy.cfg`. Changing the credentials in Ashapp replaces the server configuration and verifies authenticated access using the new values. However, **AmneziaVPN keeps already discovered service credentials locally**. Its current rescan only adds missing services and does not refresh the saved configuration for an existing one. Ashapp cannot rewrite another app's local credential store. Update the saved SOCKS5 username/password there, or remove and rediscover only that service; do not reinstall the server or expose a private proxy to work around cached credentials. This follows the official [SOCKS5 extractor](https://github.com/amnezia-vpn/amnezia-client/blob/de93650a90739b87bb47a632872ea9d0adc9412f/client/core/installers/socks5Installer.cpp) and [rescan controller](https://github.com/amnezia-vpn/amnezia-client/blob/de93650a90739b87bb47a632872ea9d0adc9412f/client/core/controllers/selfhosted/installController.cpp).

### Docker on Debian and Ubuntu

A fresh Debian 12 server's distribution Docker package may be too old for secure loopback publications or the supported shared bridge policy. Fresh installation now uses Docker's official stable APT repository for the detected Debian/Ubuntu codename, a dedicated `signed-by` keyring, and a verified pinned primary signing fingerprint. It selects an explicit stable Engine 28/29 version from the authenticated package index. No downloaded shell installer is executed. Existing Docker installations, container-runtime packages/data and foreign Docker APT sources are preserved; Ashapp refuses to upgrade, remove or restart them automatically. Repair/start an existing daemon manually when necessary. See Docker's official [Debian](https://docs.docker.com/engine/install/debian/) and [Ubuntu](https://docs.docker.com/engine/install/ubuntu/) installation documentation.

## Reinstallation and drift

Do not reinstall or upgrade this protocol from AmneziaVPN while relying on Ashapp's kernel-only guard. Administrator SSH access can replace the container, image, startup or publication. Ashapp reports changed ownership/guard state and refuses new shared-client creation and unsafe starts. It cannot prevent another administrator application from replacing a deployment.

Normal Amnezia helper-script and append-file artifacts are checked separately from engine changes. Only narrowly recognized, bounded, root-owned temporary files under protected parents are accepted. Status checks do not chmod, repair, restart or delete anything.

## Source and pins

Compatibility follows [AmneziaVPN 5.0.3.0 source](https://github.com/amnezia-vpn/amnezia-client/tree/de93650a90739b87bb47a632872ea9d0adc9412f), particularly its installation discovery, SSH uploader and WireGuard configurator. The official amd64 base image is pinned by digest in `server/amnezia_setup.py`; no mutable `latest` is used. The derived image uses narrowly selected capabilities rather than `--privileged`. The existing vendor installer byte pin and scoped APT signing-key verification remain unchanged.

## Current validation

Local checks of the development snapshot completed **213 Flutter tests**, clean static analysis and formatting, and **180 Python tests: 173 passed, 7 POSIX-only checks skipped on Windows**. Bundled helpers match their sources, the vendor checksum is unchanged, Bash syntax passes and `git diff --check` is clean. Fixtures cover kernel-only readiness and process-list failures, stock Docker networks with null IPAM configuration, deployment identity/drift, protected Amnezia uploader artifacts, setup rollback and repeated-template client matching. Process inspection requests a PID column required by Docker and rejects unavailable or empty results. The fallback check normalizes shell-specific missing-command exit codes inside the container while rejecting Docker execution errors.

On an authorized fresh **Ubuntu 24.04.5 x86_64 VPS**, kernel **6.8.0-142** and **Docker 29.1.3**, the native `WorkspaceController.provision` completed all **12 saved-template tasks** with shared mode selected. The deployment choice was overridden only in memory; the saved template and its protected answers were preserved. Five device connections and private SOCKS5 were created. The shared interface was verified as kernel AmneziaWG, the startup guard remained intact and no Go process was detected.

A temporary isolated kernel-client network namespace used one original protected client configuration to complete a VPN handshake and an **HTTPS 200** request through the shared server. The actual client interface kind was verified, the original configuration remained unchanged and the test namespace was removed. This exercises encryption and forwarding/NAT from an isolated client on the same VPS; it does not test the hosting provider's inbound UDP firewall or an external device.

A later read-only VPS check found both the shared AmneziaWG and SOCKS5 containers running, with their original container/image identities unchanged. The shared container's published UDP port **585** matched AmneziaVPN's official discovery expression. This confirms the server-side discovery inputs, not a completed GUI adoption or cross-manager edit.

Official AmneziaVPN 5.0.3.0 GUI adoption is still being verified. Published binaries, macOS runtime, reboot recovery, external VPN-client traffic and provider UDP filtering need separate validation. Earlier host-mode traffic and client-link import checks do not establish cross-manager compatibility. A successful Docker build, unit suite or reported listener does not prove these outcomes.
