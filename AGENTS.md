# Ashapp agent instructions

## Product and current status

Ashapp is a Flutter/Dart desktop application for Windows and macOS. It configures an existing Linux VPS over SSH, installs kernel-mode AmneziaWG and/or VLESS + Reality + XTLS Vision, manages per-device access, and optionally installs SOCKS5. VLESS uses a separate, pinned sing-box service and can coexist with AmneziaWG. Keep the interface approachable for users without system administration experience and support multiple servers. The app does not create VPS instances at a hosting provider.

The product's main differentiator is repeatable server preparation from reusable templates: the administrator account, protected answers, SSH/ping policy, package upgrades, protocol/SOCKS5 choices and first devices. Manual answers and templates must remain the same reviewable execution flow. Compatible VPN clients, including AmneziaVPN, handle the user's actual VPN connection; Ashapp prepares and manages the servers.

The current version is v0.0.4 with security fixes and application updates. Confirm the GitHub release and all three native assets before calling it published; never attribute these changes to old v0.0.3 archives. Windows can be built locally; macOS must be built and tested on its native CI runners. Real-VPS provisioning remains unverified. Never equate mocks or a native build with a successful server deployment. Manual setup and templates share one wizard/model/controller. Protected template answers and optional remembered SSH credentials use the OS-backed vault. Do not claim that another Amnezia application's server manager can adopt this kernel deployment or SOCKS5 without testing that integration.

The repository is public. On 2026-11-03 the owner explicitly selected the name Ashapp and authorized rewriting published Git history, tags and old release assets to use it throughout. Rebuild historical binaries from their rewritten source commits; never relabel old binaries or reuse old checksums. Preserve one source commit per version. The owner said there are no existing customers and declined compatibility/migration with the previous identity. This specific rebranding rewrite is authorized; future unrelated history rewrites still require an explicit request. Do not change visibility. Never publish credentials, private keys, local tool state or security-scan artifacts.

The owner selected v0.0.4 and authorized committing/pushing the updater and security fixes as one new version commit. `app_update.dart` owns GitHub access, release validation, streaming download, preferences and the update controller; `app_update_dialog.dart` is presentation. `tool/build_installers.py` and `tool/windows_setup.iss` produce system installers from the same native bundles as the ZIPs. Native channel `ashapp/app-update` supplies the actual build version/process architecture, opens an already verified local installer and quits. No update-signing private keys or GitHub tokens are needed by the client.

## Repository layout

- `flutter/`: Flutter application, platform runners and tests.
- `server/`: privileged server commands and VPN client management.
- `vendor/`: the pinned third-party installer and its separate license.
- `flutter/assets/`: bundled copies of the server scripts and installer. Keep them byte-for-byte synchronized with their sources. Preserve the installer checksum unless deliberately reviewing and updating the vendor version.
- `tests/`: local server and bundle regression checks. These must not connect to real servers or run privileged commands.
- `flutter/lib/server_workspace.dart`: independent session registry and active server selection. Switching must preserve other sessions.
- `flutter/lib/workspace_controller.dart`: one endpoint, serialized commands and provisioning progress. Keep orchestration out of views.
- `tool/` and `.github/workflows/release.yml`: pinned native CI, secret scans, architecture checks, provenance, source archive and checksums. Publication requires all three native targets.
- `flutter/lib/setup_wizard.dart`: the same editable question flow for manual setup and templates. Both call `WorkspaceController.provision` with the same validated models.
- `flutter/lib/credential_vault.dart`: protected SSH/template answers. `server_template.dart` and JSON repositories must never serialize those answers.
- `server/awg_setup.py`: configured installation adapter. It verifies the vendor hash and invokes only the reviewed package-install routine, then writes and verifies an IPv4-only kernel configuration. Never simulate terminal prompt answers.
- `server/vless_manager.py`: isolated VLESS service, durable UUID/Short ID state, config validation, service application and rollback. Installs checksum-pinned sing-box 1.14.4 without Docker; never adopts another proxy deployment. `flutter/lib/vless_connection.dart` is the single immutable client model for links and Xray/sing-box JSON exports.

## Product and security requirements

- Keep server profiles limited to IP addresses and ports. Keep credentials, private keys and exported VPN configurations out of JSON profiles, template metadata, logs and Git. The user has authorized remembering passwords locally: use only the OS-backed secure credential store, never a plaintext fallback. Mask passwords by default. Template credentials belong in the vault; explicit copy/export actions may reveal secrets.
- Store trusted SSH fingerprints separately. Ask before trusting a new server and reject unexpectedly changed keys. Corrupt trust stores must fail closed. Serialize and atomically replace local JSON files; merge host-key additions under the same lock.
- Send passwords through encrypted SSH stdin, never shell arguments or logs. Export or copy private configurations only after an explicit user action.
- Bind all results and client lists to the authenticated server. Preserve each session when selecting another endpoint. Reserve an endpoint before starting authentication so duplicate live or pending connections cannot bypass command serialization. Capture the controller before awaiting any dialog or confirmation. Never apply an operation to whichever server happens to be active later. Commands on different servers may run concurrently; commands on one endpoint must be serialized. Include SSH ports in endpoint identity and tests.
- Disable root SSH login only when selected and after independently verifying the new administrator's SSH login and passwordless sudo. Before any SSH mutation, reject conditional/include-expanded Match policy or unsupported syntax that prevents proving global root denial; one current-address probe cannot prove denial for other sources. Preserve the old session on failure and restore SSH configuration if validation or reload fails. Preserve the SSH connection context through sudo for administrator checks.
- Install new AmneziaWG deployments only as a kernel module. Never install a Docker/userspace VPN or replace an existing deployment. The user has authorized managing clients of existing official AmneziaVPN containers; Docker is also permitted for SOCKS5. Keep a restrictive umask and private root-owned runtime lock directory throughout configured installation. Do not add an interactive terminal or automate vendor prompts. Preserve the checksum-pinned vendor script. Do not enter its management menu or overwrite existing configurations from setup. Verify the resulting kernel interface and service. Do not promise fixed CPU consumption.
- Treat repeated setup as adding missing desired clients and preserving existing services/settings. SOCKS5 replacement must be an explicit management action. Stop at the first failing provisioning step and display what completed; do not claim full rollback of server setup. Validate all answers before any provisioning changes. Every successful account-password change must immediately update its protected credentials, including when later SSH checks fail. Initial VPN activation must clean up only its newly created configuration on failure. Preserve previous SOCKS5 running/stopped state on rollback.
- Client discovery must not depend on a running host kernel service. List saved/unmarked host peers and clients of existing official `amnezia-awg`/`amnezia-awg2` containers. Route every client action by server, source and public key; never use a display name as a container identity. Preserve both clientsTable schemas and unknown metadata. Container changes require snapshot checks, a private transaction lock, per-peer live changes without restart and verified rollback; keep backups/lock when recovery is uncertain. Do not silently overwrite concurrent edits. Preserve unavailable old private keys; root-only exports for new peers use hashed key filenames and must match the current peer/server before export. Never route container actions to host functions. Show stopped/read-failure states and stop kernel setup when an external deployment is present or discovery fails. Fixture/Bash tests do not establish real Docker/VPS compatibility.
- Save template secrets under a new immutable vault reference before atomically committing metadata. A metadata failure must preserve the previous secret generation. Never key mutable template revisions solely by display name. Retain non-secret references to pending vault deletions so a locked vault cannot permanently orphan removed answers; retry after unlocking or restarting.
- Bound SSH command output and execution time. Private exports must use a fresh protected inode and replace the destination without feeding new bytes to old readers or retaining shared permissions. Windows requires a protected owner DACL at creation and handle-based rename; reject streams/devices/reparse targets and filesystems without ACL support. macOS requires descriptor permissions and cleared extended ACL before bytes, a sandbox-aware replacement directory, and atomic installation. Preserve symlink/nonregular rejection. Keep both native helpers tested and validate the macOS save-panel flow under App Sandbox; never fall back to an ordinary plaintext file write.
- Do not modify a real server without the user's explicit request. Preserve existing services, clients and uncommitted work. MTProto is outside the current product scope.
- Updates must use stable releases from the fixed public repository only. Reject unsupported platforms, prereleases/drafts, duplicate/missing platform assets, unexpected download URLs, missing digests, oversized metadata/files and disagreement between the GitHub digest, SHA256SUMS and build manifest. Rehash before handoff; never execute release notes or remotely supplied shell commands. Restrict HTTPS redirects to known GitHub download hosts. Preserve cancellation, time/size limits and recoverable offline behavior. Update settings/cache must never contain SSH or VPN credentials. Do not describe HTTPS/checksum verification as independent signing or source-to-binary reproducibility.
- All server sessions, including inactive selections and pending connections, must be idle before update installation. Recheck immediately before handoff and gate controller operations while it is starting, including keyboard/programmatic actions. Native installer launch failure must leave the existing app open; a successful handoff is not proof that installation completed. Never force-close server tasks. Windows Setup is per-user with an app mutex; macOS packages only replace the intended application in Applications, without privileged install scripts or relocation searches. Keep native installer/OS sandbox execution gaps explicit until actually tested.
- Treat VLESS UUIDs as access credentials, not public WireGuard keys. Scope actions by endpoint, source `vless-reality` and UUID. Do not expose UUIDs through a public-key action, persist them in local profile/template JSON, or log them. Every device has a separate UUID and Short ID; export never rotates them. Build exports only from the allowlisted client model; the Reality private key and administrative data stay server-side. QR always encodes the same VLESS link, even when JSON is selected.
- Preserve independent protocol services and TCP/UDP port namespaces. VLESS, SSH and SOCKS5 require different TCP ports; AmneziaWG UDP can share the number. VLESS edits validate a staged config and restart only `ashapp-vless.service`; disclose the brief interruption to other VLESS sessions. Stopped services stay stopped during client edits. Preserve protected recovery files and a pending marker after an interrupted/uncertain transaction; do not claim revocation until service application succeeds. Do not silently overwrite manual edits.
- Use sing-box 1.14.4 as the VLESS server engine: real loopback testing confirmed both Xray 26.10.31 and sing-box 1.14.4 clients. Current Xray-server/sing-box-client Reality incompatibility must not be hidden behind a successful JSON check. The default `chrome` fingerprint has data-plane coverage. Other GUI apps/platforms and fingerprint presets need their own runtime checks. See `docs/VLESS.md` before changing engine/version pins.
- Keep the vendor installer byte pin intact. The configured Debian adapter must replace the short-ID/global apt-key bootstrap with the independently verified full PPA signing fingerprint and a dedicated Signed-By keyring for both binary/source entries. Public APT metadata must remain readable under umask077. Refuse conflicting existing sources; do not silently remove previously trusted global keys or unrelated repositories. Newly created VLESS binary ancestors and runtime directories must explicitly retain the service's required traversal/execution modes under umask077 without widening pre-existing private directories.
